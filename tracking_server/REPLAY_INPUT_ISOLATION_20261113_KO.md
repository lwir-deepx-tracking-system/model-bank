# 녹화 입력과 채점 대기 분리

## 바꾼 이유

이전 동일 접속 조건의 녹화 출력 간격은 평균 33.27ms였지만 p95는 52.30ms였습니다. 평균만으로 30fps 시간 예산을 충족했다고 할 수 없습니다. 입력 리더가 채점용 잠금을 기다리면서 입력 큐의 잠금까지 잡는 코드를 확인했습니다. 채점이 지연되면 검출 제출 스레드도 준비된 입력을 가져가지 못할 수 있습니다.

## 변경

- `src/camera/camera_extra.py`: 입력 큐 안에서는 채점 태그 등록을 기다리지 않고 시도합니다. 잠겨 있으면 입력 큐 잠금을 놓고 기다린 뒤, 소스가 바뀌거나 종료됐는지 다시 확인합니다. 태그 등록과 큐 삽입은 같은 짧은 임계 구역에서 처리합니다.
- `src/camera/replay_eval.py`: 태그 등록에 기다리지 않는 호출을 추가했습니다. 기존 호출은 그대로 사용할 수 있습니다. 채점 규칙·모델·검출 문턱·추적기를 바꾸지 않았습니다.
- `src/camera/replay_cam.py`: 선택형 `LWIR_REPLAY_PREPARE_FRAME=1`로 다음 한 장을 예정 시각 전에 읽습니다. 추가 준비 이미지는 한 장으로 제한하고, 일시정지 때 보존하며 탐색 때 폐기합니다. 읽기와 시간 대기 뒤에 제어 명령을 다시 확인합니다. 기본값은 꺼짐이고 `--no-skip` 무손실 녹화에서만 작동합니다.

CPU 코어 배치·RAW16 밝기 변환·해상도·JPEG 크기는 변경하지 않았습니다. 채점이나 표시할 프레임을 버려서 시간을 줄이는 방식이 아닙니다.

## 적용과 확인

입력 잠금 수정은 서버 코드를 갱신하고 재시작하면 적용됩니다. 이미지 준비는 `scripts/live.env`에 다음을 추가한 뒤 서버를 재시작합니다.

```bash
export LWIR_REPLAY_PREPARE_FRAME=1
```

새 재생 로그의 `REPLAY frame preparation on`과 `lossless on`을 함께 확인합니다. 실행 중인 재생에는 소급 적용하지 않습니다. 환경값을 0으로 바꾸고 재시작하면 원래 이미지 준비 순서로 돌아갑니다. 이 옵션은 물리 카메라의 프레임 속도를 바꾸지 않습니다.

## PC 검증

원래 코드에서 평가 잠금 중 입력 큐 접근 검사가 실패하는 것을 확인했고 수정본에서 통과했습니다. 교체된 재생 소스, 꽉 찬 큐, 태그·프레임 순서, 되감기, 일시정지와 마지막 프레임을 검사했습니다. 25ms PNG 읽기 지연을 주입한 모의 시험에서는 해당 간격 약 58~59ms가 33~34ms로 줄었지만 이는 M1 실측이 아닙니다. 준비 전후 픽셀과 순서는 같았습니다.

관련 통합 회귀 107개가 Windows에서 통과했습니다. 첫 통합 실행은 테스트의 상대 `images` 경로가 저장소의 문서 그림 폴더를 읽어 무손실 조건을 충족하지 못했습니다. 테스트 전용 임시 폴더와 숫자 PNG 파일명을 사용하고 무손실 조건을 명시 확인하도록 수정한 뒤 같은 명령을 통과했습니다. 운영 코드를 테스트에 맞춰 완화하지 않았고 처음 실패 기록은 보존했습니다. 두 수정은 서로 다른 담당자가 작성하고 교차 검토했습니다.

장치 배포와 동일 영상 비교 결과는 완료 후 이 문서에 추가합니다. p95 33.3ms 달성은 아직 확인하지 않았습니다.

## 남은 범위

- `/replay/seek` 요청의 기존 잠금 순서는 유지합니다. 사용자 탐색 순간의 대기는 이번 정상 재생 최적화와 구분합니다.
- PNG 한 장을 이미 읽거나 파이프에 쓰는 동안 들어온 명령은 해당 작업이 돌아온 뒤 반영됩니다.
- 압축 RAW 파일의 먼 탐색 비용, 장시간 재생, 물리 카메라와 브라우저 표시 지연은 별도 확인이 필요합니다.
- CPU 작업별 배치와 RAW16 변환 최적화는 미적용입니다. 실제 단계별 대기 근거를 확보하고 픽셀·채점 동등성을 검증한 뒤 선택합니다.
