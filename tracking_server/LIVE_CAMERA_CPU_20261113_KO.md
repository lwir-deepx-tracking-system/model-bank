# 실시간 카메라 경로의 대기·CPU 작업 점검 (2026-11-13)

## 결론과 현재 범위

실카메라에서도 사용하는 외형 추출 경로에 같은 프레임의 크롭을 최대 두 개 먼저 제출하는 선택 기능을 추가했다. 검출기, 외형 가중치, 크롭 좌표·보간·정규화, 최종 ID 판정 순서는 유지한다. 기존 NPU2 갱신 엔진의 여유 슬롯을 사용하므로 새 모델을 추가하지 않는다. 모든 특징을 받은 뒤 기존 판정기를 호출한다.

이 문서 최초 작성 시점: PC·ARM64 회귀 각 118개, 격리 NPU2 비교 완료. 운영 활성화·전체 추적 비교는 다음 배포 확인에 기록한다. 실제 카메라는 USB 목록에 없으므로 센서→USB→최종 화면 지연은 측정하지 않았다. **33.3ms 달성이나 실제 카메라 개선 완료를 주장하지 않는다.**

### 배포 점검 후 현재 상태

**운영 적용 완료 (`fb4e472`):** 팀원 GUI를 유지한 main 코드를 장치에 반영했다. 실제 자동 실행기도 최신 배포 폴더로 전환하고 교대 투입·카메라/재생 비동기 미리보기·녹화 사전 준비·같은 프레임 외형 크롭 선제출을 켰다. 선택된 실내 YOLO26m·Python ByteTrack·ViT Lite FT, 짐벌 바이너리/실행 인자 및 라벨 서버를 보존했다.

현재 선택 설정의 같은 280프레임(23fps 요청)을 적용 전후 각각 완주했다. 두 회차 모두 280장을 발행·채점했고 서버 누락·순서 오류는 0이었다. 후보 회차는 NPU0·1 각각 140장씩 새로 제출했다. FP65/FN38/IDSW10/HOTA68.6911/IDF1 94.11/AP50 96.3062/AP50:95 51.5595가 모두 일치했고 ID 변경 사건 목록도 같았다. 이는 저장 영상의 집계 지표·사건 동등성이지 모든 내부 좌표의 비트 단위 동등성 증명은 아니다. 새 외형 추출 경로 활성 로그도 확인했다.

| 저장 영상 측정 구간 | 적용 전 평균 / p95 | 적용 후 평균 / p95 |
|---|---:|---:|
| 입력 수신 → 추적 결과 | 52.02 / 71.18ms | 37.05 / 49.96ms |
| 결과 출력 간격 | 43.78 / 67.60ms | 43.72 / 56.19ms |
| 프레임 처리 구간 | 34.38 / 44.28ms | 29.28 / 38.98ms |

양쪽 시청자는 시작·종료 시 1명이었다. 다만 고정 순서의 전후 각 한 회이고 재시작·코어 투입·표시 방식이 함께 달라져 순수 외형 크롭 병렬화의 인과적 효과로 해석하지 않는다. 23fps 입력의 주기는 약 43.48ms다. **실카메라는 USB에 없으며 p95 33.3ms를 달성한 결과가 아니다.**

이전 두 재시작 원인도 확인했다. 11:03·11:11 로그는 녹화 HOLD 상태를 출력 멈춤으로 오판한 자동 복구였다. 새 watchdog은 같은 녹화가 일시정지/끝 프레임에 있고, 입력 수가 유지되고, 대기열이 비었을 때만 그 검사를 제외한다. 실제 재생/라이브 처리 멈춤은 기존대로 검사한다. 이전 일시중지 파일 제거 원인은 미확인으로 유지한다.

첫 수정의 11개 모의 검사는 통과했으나 실제 비동기 종료 응답은 `pos=null, shown=280, total=280`이었다. 이를 놓쳐 11:21 자동 재시작이 한 번 더 발생했고 새 옵션은 재시작 뒤에도 유지됐다. 실패 표본을 보존하고 `shown` 종료 표현을 보완했다. 추가로 현재 입력 수와 같은 재생의 수신 집계를 맞춘 뒤, 처리되거나 누락으로 정산된 입력만으로 전부 설명되는지 확인한다. 따라서 마지막 프레임이 대기열에서 빠진 뒤 처리가 멈춘 경우와 오래된 집계도 정상 종료로 간주하지 않는다. PC·ARM64 모의 22개 검사를 통과했다. 미완료 shown, 명시된 미완료 pos, 새 입력 증가, 대기열 잔류에서도 기존 검사를 유지한다. 현재 사용자 재생을 바꾸지 않고 watchdog만 교체하며, 실제 유지 관측과 모의 EOF 검사를 구분해 기록한다.

### 이전 적용 시도의 기록

최신 갱신: 사용자 재승인 후 팀원의 `9361513` 프레임 넘기기 GUI를 통합한 `82ecd90`을 main에 올렸다. 연속 STEP·PLAY·SEEK 경계를 수정했고 PC 기존 118개 및 관련 17개 검사, ARM64 통합 120개 검사를 통과했다. 서로 겹치는 PC 검사 수를 합산하지 않는다.

실제 자동 실행기는 최신 배포 폴더와 다른 복사본을 실행하고 있어 기존 지연 옵션이 꺼져 있었다. 그 복사본에서 현재 선택된 실내 YOLO26m·SORT Python·ViT Lite FT를 유지해 저장 영상 280장 기준선을 완료했다. FP37, FN78, IDSW6, HOTA49.9795, IDF1 66.98이며 이는 **적용 전 기준선**이다. 이후 배포의 종료·교체 단계를 실행하기 전에 작업용 재시작 대기 파일이 사라졌고 서버 instance가 두 차례 바뀌었다. 원인을 특정 사용자로 추정하지 않았으며 현재 실행을 덮어쓰지 않았다. 다른 재시작 작업과 조율해야 한다. 운영 적용과 적용 후 동등성은 아직 미완료다. 아래 문단은 이전 시점 기록이다.

코드 `13d3f93`은 main에 올렸다. 격리 시험 뒤 기존 코드의 8090을 복구하고 원래 시퀀스의 완주를 확인했다. 이후 최종 배포 직전 해당 실행이 종료됐고, 기존 자동 실행기 아래에서 새 서버가 시작됐으며 짐벌 실행 인자도 바뀐 것을 관측했다. **새 서버는 건드리지 않았고 최적화 옵션도 켜지 않았다.** 팀 작업과 충돌하지 않도록 조율 중이다. 전체 추적의 전후 동등성 비교는 미완료이며, 격리 특징 비교를 대신 근거로 삼아 완료 처리하지 않는다. 8770 라벨 서버의 PID·생성 시각은 유지됐다.

실행 중 선택이 OC-SORT로 바뀐 기록도 있어, 앞서 확인한 Python ByteTrack 구성을 현재 설정으로 고정해서 배포하면 안 된다. 다음 담당자는 최신 선택과 자동 실행 상태를 읽고 시험 범위를 다시 맞춰야 한다. 새 코드의 장치 적용·활성화·전체 결과 검증을 서로 구분한다.

## 현재 스케줄과 남은 대기

1. 입력 스레드가 프레임을 준비하고 NPU0·1에 교대로 넣는다. 결과는 원래 프레임 순서로 받는다.
2. CPU에서 카메라 움직임 보정과 ByteTrack을 적용한다.
3. 필요한 사람 크롭의 RepVGG 특징을 NPU2에서 받아 기존 재연결 판정을 한다. 종전의 `--rl-async`는 주로 기존 ID의 특징 갱신을 다음 프레임까지 겹치는 기능이었다. 같은 프레임에 필요한 신규 특징은 직렬 대기가 남아 있었다.
4. 추적 결과 발행 뒤 웹 영상 준비·압축을 분리한다. 표시할 필요가 없는 프레임에서는 표시용 좌표·색 변환을 생략한다.

두 검출 코어의 교대는 처리량을 돕지만 한 프레임 자체의 검출 시간을 절반으로 만들지 않는다. 낮은 NPU 사용률만으로 낭비라고 판단할 수 없고, 오래된 프레임을 쌓지 않는 대기 제한도 필요하다. GMC 대기, 실제 USB 입력 간격, CPU 경합, 화면 전송 지연은 여전히 별도 계측 대상이다. 최초 격리 시험 때의 선택은 Python ByteTrack·RepVGG였고 Mamba는 꺼져 있었다. 최신 적용 전 기준선은 위의 SORT Python·ViT Lite FT이며, 설정을 다시 읽지 않고 과거 선택으로 덮어쓰지 않는다.

## NPU2 격리 비교

동일 M1, 동일 `REPVGG_DISTILL_INSIDE_20261110`, 저장된 RAW16 24프레임의 같은 두 사람 크롭. 모든 요청 특징이 반환됐는지 확인했다. 각 방식 2회, 회당 72프레임을 기존/후보/후보/기존 순서로 측정했다. 별도로 48개 특징 벡터가 원소 단위로 완전히 같았으며 최대 차이는 0이다.

| 두 크롭을 준비하고 특징을 받는 구간 | 기존 직렬 | 두 요청 선제출 |
|---|---:|---:|
| 평균 | 6.530ms | 2.556ms |
| p50 | 6.414ms | 2.410ms |
| p95 | 8.860ms | 3.621ms |

이는 두 구현 경로의 비교다. 기존 경로에만 크롭별 NPU 계측 API 호출이 있고 새 경로는 배치 전체 벽시계 시간을 따로 남기므로, **절감 전체를 순수한 NPU 병렬 계산 효과로 해석하지 않는다.** 단일 NPU 코어의 서로 다른 요청이며 물리 코어 두 개로 계산한 결과도 아니다. 검출과 동시에 구동하지 않은 격리 시험이므로 전체 파이프라인 감소량으로 더하거나 p95끼리 빼서 예측하지 않는다.

같은 프레임에 두 특징이 실제로 필요한 경우에는 이 단계의 평균 대기가 약 4ms 줄어들 가능성이 있다. 특징 요청이 없거나 하나인 프레임은 이 개선의 대상이 아니다. 실제 장면에서 그런 프레임의 빈도를 확인해야 전체 평균 효과를 추정할 수 있다.

시험의 RAW16→8 변환은 양쪽에 동일한 크롭을 제공하기 위한 고정 시험 입력이며 운영 전처리를 바꾼 것이 아니다.

## 채택하지 않은 전처리 후보

PC에서 임시 배열을 줄인 RAW16 변환은 빨랐지만 Orange Pi에서는 평균 1.342→1.537ms로 느려졌다. 단순화한 두 번째 후보도 1.387→1.477ms로 느려져 운영 코드에서 제외했다. 두 후보 모두 픽셀·밝기 추정값의 동등성은 통과했다. 실패 후보와 측정 자료를 보존한다.

## 표시 준비 정리

108개 조건에서 기존/수정 JPEG 바이트, 프레임 번호, 제어 입력, 평가 입력이 같았다. 실제 JPEG 압축·NPU·제어 장치 비용을 제외한 ARM64 함수 시험에서 12명·미리보기 있음 조건은 약 92.9→87.3µs, 미리보기 불필요 조건은 83.2→39.7µs다. 작은 절약이며 33ms 문제를 단독 해결하지 않는다. 팀원이 수정 중인 GUI 레이아웃과 재생 요청 경로는 바꾸지 않았다.

## 운영 옵션과 오류 처리

`scripts/live.env`의 `export LWIR_REID_BIRTH_PIPELINE=1`로 선택한다. 현재 시작 환경 옵션이라 첫 적용에는 서버 재시작이 필요하다. `--rl-async`가 없거나 기존 갱신이 아직 실행 중이면 기존 직렬 엔진을 사용한다. 끄려면 0으로 바꾸고 재시작한다. 첫 실제 사용은 `REID same-frame pipeline active` 로그로 확인한다.

SDK 제출·결과 대기에 실패해 완료가 불명확해진 비동기 엔진은 격리한다. 알려진 다른 요청만 한 번 회수하고, 해당 엔진의 새 제출·수집을 막아 사용 중인 버퍼 덮어쓰기를 방지한다. 그 오류가 상위 실행 경로에 전달될 수 있으며 무중단 복구를 보장하는 기능은 아니다. 정상 결과 특징은 재사용 슬롯과 독립된 배열을 소유한다.

기존 `rl_crop_ms`/`rl_npu`에는 직렬 호출만 기록된다. 새 배치 기록 `birth_pipeline_batches`는 최대 512개를 유지하는 별도 벽시계 기록이다. 옵션을 켠 뒤 직렬 크롭 수가 줄었다고 총 ReID 요청이 줄었다고 해석하면 안 된다.

## 다음 검증

동일 저장 시퀀스·검출·추적 설정에서 운영 경로를 비교하고 FP/FN/IDSW·HOTA/IDF1/AP 및 ID 변경 사건을 대조한다. 이것은 저장 영상 회귀 검증이며 모든 실카메라에서의 ID 동등성을 보장하지 않는다. 카메라가 연결되면 같은 조건에서 입력 수신→추적 발행 지연과 출력 간격 p95를 별도로 측정한다. 모델·제어 튜닝, RAW16 변환, GUI 레이아웃, 라벨 서버는 이번 변경 대상이 아니다.
