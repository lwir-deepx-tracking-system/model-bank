# 예측 제동 보정: 구현과 검증 범위

현재는 **예측 제동 v2의 코드 검사를 마쳤고, 실제 보정 전후 성능 비교는 끝내지 못한 상태**다. 기본값은 꺼짐이다. 기존 PD 30/0/6과 운영 LEAD 꺼짐을 유지했으며 새 보정값을 운영에 채택하지 않았다.

## 고친 동작

`--predictive-brake 1`은 중심에 접근 중인 가로 이동을 조금 먼저 정지시키는 시험 기능이다. 새로운 이동이나 속도 증가를 만들지 않는다. 50ms 접근 예측, 640폭 기준 최대 4px의 선행 정지 구간, 직전 SPD 1–7이라는 제한을 유지한다. 두 관측 구간에서 접근 중임을 확인하며, 새 관측으로 계산한 정지 유지 구간은 최대 100ms다. 새 관측이 바깥으로 움직이면 기존 추종으로 복귀한다. 같은 프레임만 반복되면 STOP을 유지하며 기존 입력 만료 검사로 넘어가므로, 100ms가 지나면 관측 없이 움직이는 방식은 아니다.

첫 후보 v1에서 드러난 두 가지를 v2에서 수정했다.

1. **프레임 번호와 관측 시간을 구분했다.** 실행기가 최신 관측을 처리하면서 중간 번호를 건너뛰어도, 번호가 증가하고 실제 관측 간격이 10–100ms이면 속도 이력을 이어간다. 명시적인 사람 누락·중복 ID·무효 관측은 뒤의 정상 관측에 덮여도 이력을 초기화한다.
2. **중심 근처의 미분항 반전을 먼저 정지로 처리한다.** 실제 위치 오차의 방향과 P+I는 같은 방향인데 D 때문에 반대 방향 명령이 된 경우만 다룬다. 이미 중심으로 이동하고 있고 선행 정지 구간에 있을 때 먼저 멈춰 새 관측을 확인한다. 대상이 실제로 바깥으로 움직이거나 반대편으로 넘어가면 기존 제어로 돌아간다.

기존 `--observation-grace-ms 100`의 보호 정지는 바꾸지 않았다. 그 경로에서 수신 처리 전에 번호가 빠지면 기존 시퀀스 단절 STOP이 먼저 작동한다. 수신 처리 후 제어 평가만 건너뛴 경우와 구분해야 한다. 유예를 끈 시험만으로 운영 환경의 개선을 주장할 수 없다.

## 실제 기록에서 확인한 근거

가상 표적을 실제 카메라와 짐벌로 따라간 첫 A 블록의 일부 기록이다. 시험은 완료되지 않았으므로 성능 대조 결과가 아니다.

| 관측 | 기존 제어에서 일어난 일 | 수정 근거 |
|---|---|---|
| 153번, 가로 오차 +21.58px | 두 구간의 접근 속도 약 304·272px/s. 기존 PD는 이미 반대 방향을 요구했고 발행 약 20.82ms 뒤 반전 STOP, 그 뒤 반대 방향 SPD 1, 154번에서 일반 중심 구간 STOP | v1은 PD의 같은 방향 요구만 허용해 발동하지 않았다. v2는 미분항 때문에 생긴 이 반전을 먼저 제동하는 조건을 추가했다. |
| 192번, 가로 오차 −19.66px | 191번 관측은 발행됐으나 제어 평가 기록에 없었다. v1은 190→192 번호 단절로 예측량을 0으로 만들었다. 193번에서 일반 STOP | 관측 시각으로 판단하도록 바꿨다. 다만 191번이 수신 처리됐는지는 당시 기록으로 구분되지 않는다. |

## 검사와 실행

- Windows와 ARM64: 신규 예측 제동 회귀, 기존 제어 9건, ARM64 실제 브리지의 명령 인수·LEAD 가상 직렬 검사 통과.
- 중간 정상 관측 덮어쓰기, 명시적 누락 덮어쓰기, 110ms 간격, OBS 무효, 미분항 반전, 바깥 이동 즉시 해제, 기본 OFF 동작을 검사했다.
- 시험 도구: PC/ARM64 10개 검사 통과. 실제 브리지 + 합성 영상의 가상 실행과 실제 카메라 실행은 별도 기록이다.
- 실제 비교 1차: A 블록 진행 중 관측 발행 65ms 한도를 넘어 정지. RAW16 226장과 중복 원본 33장을 보존했고 최종 정지 영상과 서버 복구를 확인했다. 같은 원본의 ARM 재계산에서 해당 프레임 정합은 8.82–10.32ms였으나 당시 약 105ms 지연의 원인은 확정하지 못했다.
- 이후 시험 도구에 단계별 시각 기록과 프로필 처리 스레드만의 CPU 지정 기능을 넣었다. 65ms 발행 한도·180ms 새 관측 감시는 유지한다. 카메라·브리지·감시 스레드의 CPU 배정을 함께 바꾸지 않는다.
- 실제 비교 2차: 카메라 열기에서 `libusb_timeout`, 원본 0장으로 중단. 비교 블록과 이동 명령을 시작하지 못했다.

카메라 복구를 위해 기존 초기화 기능을 호출했으나, USB 초기화 실패 후 그 기능의 전체 USB 전원 재시작 단계까지 실행됐다. 짐벌 직렬 연결도 끊겼다가 정지 상태로 복구됐다. 카메라는 USB 목록에 돌아오지 않았다. 이후 추가 초기화나 물리 시험을 하지 않았으며 카메라 케이블 재연결을 기다린다. 8770 라벨 서버는 유지됐다.

## v2의 장치 없는 폐루프 결과

ARM64 실제 브리지 바이너리와 합성 카메라/가상 직렬을 사용한 결과다. 모터·카메라 실기 수치가 아니다. 시험 처리 스레드는 같은 CPU 범위를 사용했고 원래 배정으로 복구됐다. 제동 후보가 발동한 B3에서 일부 수치는 낮았지만, 다른 B에서는 발동하지 않았고 전체 판정은 개선 미확립이다.

| 순서 | 보정 | 중심 MAE px | 중심 p95 px | 중심 범위 안 비율 | 전체 영상 이동 px | 정지 구간 초과 이동 px | 예측 STOP |
|---|---|---:|---:|---:|---:|---:|---:|
| A1 | 끔 | 16.88 | 47.78 | 76.67% | 157.03 | 1.56 | 0 |
| B2 | 켬 | 17.28 | 43.97 | 77.45% | 166.56 | 0.00 | 0 |
| B3 | 켬 | 14.90 | 42.74 | 76.57% | 160.02 | 0.00 | 1 |
| A4 | 끔 | 17.16 | 42.51 | 77.09% | 166.36 | 0.00 | 0 |

B2처럼 예측 STOP이 없는 블록의 차이는 새로운 보정의 효과로 세지 않는다. 이 합성 결과나 테스트 통과를 실기 튜닝 완료로 표현하지 않는다.

## 다음 실기 비교

카메라 원본이 다시 들어오고 현장 정지 준비가 확인된 상태에서만 새 결과 폴더로 수행한다. [A/B 규약](PREDICTIVE_BRAKE_PROTOCOL_20261112_KO.md)의 A→B→B→A 순서로 중심 오차 MAE·p95·중심 허용범위 비율, 정착 오차, 정지 구간의 왕복 이동, 재출발·반전과 실제 예측 STOP 수를 함께 본다.

시험 도구의 `provisional_improvement` 문자열만으로 채택하지 않는다. 그 판정은 MAE·p95 비악화를 보장하지 않으며, 한쪽 B에서만 발동하면 다른 쌍의 차이를 보정 효과로 해석할 수 없다. 실제 사람·세로·고속·운영 관측 유예 조건의 효과도 미검증이다. 카메라 수신 기준 지연은 센서 노출 지연이나 모터 자체의 제동 시간과 다르다.

원본 RAW16·장치 주소·개인 실행 경로는 공개 저장소에 포함하지 않는다.
