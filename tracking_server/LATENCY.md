# 지연(레이턴시): 잰 값과 실제 카메라일 때의 추정

"도착 → 결과"는 영상 한 장이 서버에 도착한 때부터 결과(상자와 번호)가 나간 때까지입니다. 카메라가 영상을 만드는 시간은 들어 있지 않습니다.

## 2026-11-13: 실시간 미리보기 대기 분리 — 장치 적용, 실영상 측정 대기

`LWIR_ASYNC_PREVIEW=1`을 켜면 실시간 카메라의 박스 그리기와 JPEG 압축을 별도 작업 스레드에서 처리합니다. 기본은 꺼짐입니다. 녹화 재생은 옵션과 관계없이 기존처럼 현재 프레임의 JPEG를 만든 뒤 진행합니다.

검출·추적·평가 입력은 그대로 처리하며, 화면 표시만 처리 중인 한 장과 가장 최근의 대기 한 장을 유지합니다. 압축이 밀리면 오래된 표시 대기를 교체합니다. 영상 소스 전환이나 종료 뒤에는 이전 작업의 그림이 새 화면을 덮어쓰지 않도록 검사합니다.

시간 지표를 구분합니다. `/perf`의 `delay_kind=tracker_output`은 서버 도착부터 추적 결과 처리 시점이고, `/healthz`의 `delay_kind=jpeg_ready`는 서버 도착부터 JPEG가 준비된 시점입니다. 둘 다 브라우저에 실제 표시된 시각은 아닙니다. 원본과 짝지을 시각이 없으면 지연을 0으로 기록하지 않습니다.

이 변경은 **추적 루프의 압축 대기를 줄이는 후보**입니다. JPEG 준비 시간도 함께 줄어든다는 보장은 없습니다. `da5d3c5`를 장치에 적용하고 두 지연 옵션을 켠 뒤 실제 프로세스 설정·시작 로그·8090 응답과 장치 회귀 67개를 확인했습니다. 카메라가 USB 목록에 없고 입력은 0장이므로 적용 후 실제 영상 지연은 아직 측정하지 못했습니다. 아래 실제 카메라 수치는 이 변경 이전 기록입니다. 예측 제어 실기 튜닝은 사용자 지시로 보류 상태입니다.

저장 영상 218장 전체의 JPEG·제어 입력·평가 입력 일치, 회귀 67개와 독립 검토를 확인했습니다. [전후 시간·표시 누락·적용 한계](ASYNC_PREVIEW_20261113_KO.md)를 함께 읽습니다.

## 다음 프레임 대기 제거

기본 실시간 실행에서는 다음 프레임이 이미 큐에 있을 때만 먼저 제출합니다. 큐가 비어 있으면 현재 결과를 발행한 뒤 다음 입력을 기다립니다. 녹화 재생에서도 입력이 비어 있을 때 현재 결과가 먼저 발행됩니다.

이 동작은 `--pipeline --no-vit --npu-depth 1 --live-wait 0`인 웹 서버에서 기본으로 켜집니다. `--zoom`이나 `LWIR_NPU_FEED=arrival`을 쓸 때는 적용되지 않습니다. 기존 순서로 돌아가려면 `scripts/live.env`에 `export LWIR_LIVE_READY_PREFETCH=0`을 추가합니다.

PC에서 카메라와 NPU를 모의 실행해 입력 지연을 재현했습니다. 지연을 넣은 한 프레임에서 검출 완료부터 JPEG 발행까지 약 260 ms에서 3.6 ms로 줄었습니다. 아래 M1 실측은 수정 전 값입니다. 수정 후 M1에서 한 프레임의 지연과 연속 출력 간격은 다시 측정해야 합니다.

## 실제 카메라로 잰 값 (2026-11-12 08:40, 가장 믿을 값)

카메라가 돌아와서 **실제 카메라로 직접** 쟀습니다. 장치에서 서버를 단계별 시간 재기(`LWIR_STAGE_TIMING=1`)와 카메라 시간표(`LWIR_CAM_STAMP=1`)를 켜고 약 3분(4,672장) 돌렸습니다. 조건: 짐벌 연결됨(아무도 안 따라감), **웹 화면 보는 사람 5~6명**(그림을 매 장 만듦), 초당 22장, 중간값 / 늦을 때(p95).

- **카메라 → 서버 도착: 1.5 ms** / 3.5 ms — 카메라 프로그램이 장을 받은 때부터 서버가 다 받을 때까지.
- **도착 → NPU 에 넣음: 6.1 ms** / 26 ms
- **NPU 검출: 27.1 ms** / 38 ms
- **상자 풀기 + 다음 장 기다림: 17.4 ms** / 52 ms
- **추적 전 준비: 0.6 ms** / 0.9 ms (보이는 사람이 적어 온도 Filter 가 거의 안 걸림)
- **추적: 4.6 ms** / 9.4 ms
- **번호 잇기: 1.0 ms** / 2.2 ms
- **내보내기: 15.7 ms** / 22.6 ms (화면 그림 + 짐벌 전송)
- **합계 도착 → 결과: 79.7 ms** / 113 ms

**위 "추정"과 비교**

- 추정 61 ms(화면 보는 사람 있음) 보다 **약 19 ms 큽니다.** 큰 쪽은 "다음 장 기다림" +5 ms(실제 카메라는 22장/초라 장 사이가 길고 흔들림), "NPU 에 넣기까지" +3 ms, 추적 +3 ms, 내보내기 +3.5 ms(짐벌 전송이 들어감) 입니다.
- 짐벌 전송 비용은 따로 재지 않았고, 내보내기가 재생 때(12.0 ms)보다 3.7 ms 큰 것이 짐벌 전송 몫의 상한으로 보입니다.
- 카메라 시각 이전(센서가 영상을 만들어 카메라 프로그램에 닿기까지)은 소프트웨어로 잴 수 없습니다. 카메라 프로그램이 장을 받은 시각이 가장 이른 기준입니다.

## 어떻게 쟀나

- 장치(DX-M1, 진짜 NPU)에서 **저장된 실외 녹화(seq_018)를 카메라처럼 재생**해 잰 값입니다 (2026-11-12, 180초 × 3번, 초당 25장, 중간값).
- 아래 "단계별 값"은 카메라가 없던 때(11-11 19:54 ~ 11-12 08:30) 저장된 녹화로 잰 값과 그 추정입니다. 재생과 실제 카메라는 다른 부분이 있어서 그 부분을 따로 떼어 "실제 카메라일 때의 추정"을 적었습니다. 카메라가 돌아온 뒤 위의 실제 값을 쟀습니다.
- 표시: **[잼]** 장치에서 잰 값, **[추정]** 계산이나 다른 값에서 어림한 값, **[모름]** 재지 못함.

## 단계별 값

각 항목: 재생에서 잰 값 → 실제 카메라일 때 추정, 이유.

**1. 카메라 → 서버에 도착**
- 재생에서 **1.8 ms [잼]**: 재생 프로그램이 파이프로 한 장(614 KB)을 쓰는 시간.
- 실제 카메라: **1.5 ms [잼]** (위 "실제 카메라로 잰 값"). 센서가 영상을 만들어 카메라 프로그램에 닿기까지는 소프트웨어로 잴 수 없습니다.
- 11-11 에 실제 카메라로 읽은 "도착 → 화면 그림"은 중간값 약 75 ms 였고, 재생에서 잰 "도착 → 결과"는 72 ms 로 비슷했습니다. 서버 안의 시간은 재생과 실제가 크게 다르지 않다는 근거입니다.

**2. 도착 → NPU 에 넣음**
- 재생 **3.2 ms [잼]** → 실제 **3 ms [추정]**. 서버 안의 일이라 같습니다.

**3. NPU 검출 (코어 0)**
- 재생 **29.5 ms [잼]** → 실제 **30 ms [추정]**. 같은 모델, 같은 크기의 입력이라 같습니다.

**4. 상자 풀기 + 다음 장 읽어 넣기**
- 재생 **12.0 ms [잼]** → 실제 **12 ms [추정]**.
- 다음 장이 도착할 때까지 기다리는 시간이 들어 있어서, 영상이 도착하는 간격에 따라 달라집니다. 재생은 25.0장/초로 일정하고, 실제 카메라는 22~24장/초로 조금 흔들렸습니다.

**5. 추적 전 준비 (온도 Filter 등)**
- 재생 **7.6 ms [잼]**. 이 가운데 온도 Filter 가 6.8 ms 였습니다.
- 재생 녹화는 한 장에 사람이 평균 4명, 많을 땐 9명입니다. Filter 계산이 사람 수에 비례해서 사람이 많은 장면의 값입니다.
- 실제 장면(사람 1~2명)이고 **11-12 에 고친 빠른 계산**이면 **약 1 ms [추정]**. 고친 계산은 상자 하나에 136 → 28 μs 로 PC 에서 잰 값이고, 장치에서는 아직 안 잼.

**6. 추적**
- 재생 **2.9 ms [잼]** → 실제 사람 1~2명이면 **1~2 ms [추정]**. 사람 수에 대체로 비례합니다.

**7. 번호 잇기 (외형 비교)**
- 재생 **2.0 ms [잼]** → 실제 **1~2 ms [추정]**. 사람 수에 비례합니다.

**8. 내보내기**
- 재생 **12.0 ms [잼]**. 이 값에는 웹 화면용 그림 만들기(색 그림 6 ms + JPEG 5 ms)가 들어 있었고, 짐벌은 붙이지 않아서 짐벌 전송은 0 이었습니다.
- 실제 카메라:
  - 웹 화면을 보는 사람이 **없으면** 화면 그림이 1초에 한 장이라 **약 0 ms**. 11-12 에 고친 것이고 장치에서는 아직 안 잼 **[추정]**.
  - 웹 화면을 보는 사람이 **있으면 약 11 ms [잼]**.
  - **짐벌 전송**: 한 장마다 원본 영상 614 KB 를 짐벌 프로그램에 파이프로 넘깁니다. **0.5~1 ms [추정]**, 실제로는 **[모름]** (짐벌을 붙인 채로 재지 못함). 영상을 팀 PC GUI 로 보내는 인코딩은 짐벌 프로그램 안에서 돌아 서버의 한 장 처리 시간에는 안 들어가지만 CPU 를 나눠 씁니다.
  - 기록 정리 0.4 ms **[잼]**.

## 합계

| 경우 | 도착 → 결과 중간값 |
|---|---|
| 재생에서 잰 값 (사람 평균 4명, 화면 그림 매 장) | 72 ms [잼] |
| 실제 카메라, 사람 1~2명, 화면 보는 사람 없음 (11-12 고침 적용) | **약 50 ms** [추정] |
| 위와 같고 화면 보는 사람 있음 | **약 61 ms** [추정] |

**추정의 계산** (보는 사람 없음): 3 + 30 + 12 + 1 + 1.5 + 1.5 + (0.4 + 0.8) ≈ 50 ms.

## 알아 둘 것

- **녹화를 재생하는 동안 화면에 보이는 지연(중간값 156~171 ms)은 실제 카메라일 때보다 훨씬 큽니다.** 재생 중에는 이런 것이 더해집니다:
  - 정답 채점이 CPU 를 씁니다.
  - 화면을 보는 사람이 있으면 매 장 화면 그림을 만듭니다.
  - 재생 프로그램이 PNG 를 읽고 풀어 CPU 를 씁니다.
  - 그래서 재생 중 지연으로 실제 지연을 말하면 안 됩니다. 지연은 위 표의 방식(화면을 안 보는 상태에서 단계별 시간 재기)으로 잽니다.
- 카메라가 돌아오면 `LWIR_STAGE_TIMING=1` 로 같은 단계를 다시 재서 위 **[추정]** 을 **[잼]** 으로 바꿉니다. 그때 카메라 시각(`LWIR_CAM_STAMP=1`)도 같이 켜면 1번 "카메라 → 서버에 도착"도 잴 수 있습니다.
- 짐벌 쪽 지연(영상이 짐벌에 도착해 명령이 나갈 때까지)은 이 글에 없습니다. 짐벌 시험 도구(`src/gimbal/hil_test/`)로 따로 잽니다.
